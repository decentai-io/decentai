11 · Secrets and data

Two halves, and one call at a time

Records, files, secrets and skills are kinds of one document, so that what must be right is written once: the organization, who sees it, who may change it, and encryption. A secret's encrypted half is never read back to a person, under any permission. It is handed to one agent's run, for one call.

What an agent keeps is under its own slot, <ref>__<resource>. Its ref is its approval's, so two agents' notes never meet, even for one person.

A credential you type

An API key or a password goes to the agent's run as typed, since an agent can't use a key without having it. Reading the agent before approving it is the control for what it does with one.

A connected account

You sign in with the provider once. The platform keeps and refreshes the tokens. The refresh token never leaves the API server, and the agent receives only an access token.

A shape is no access

A manifest declares the shape of the credential it needs. Which saved credential answers is a person's grant to that slot, offered only where the shapes match exactly.

A login, as it works

A browser agent may ask for a site's login on a card. Which agent may use it on which site is the person's say. A field marked not to be remembered is written nowhere.

Mechanism

Reading a secret

api_server/src/data/secrets.py · data/credentials.py

Only a runtime, in a chat, gets the values, and only by endpoints no person can call. Secrets:Secret:Use and Secrets:Credential:Resolve are declared Only for a runtime, so a person calling one is refused whatever their policies say. Each use writes a line naming the secret and the chat.

Secrets:Secret:Use
{"chat_id": "chat_8d2f", "resource_id": "agt_3__mail"}
→ {"keys": {"host": "mail.acme.example"}, "values": {"token": "..."}}

Which secret answers for a slot is settled in order: the one the chat chose, one granted to the agent, the person's default, then the only one they can see. Two or more with nothing to choose between them is a 409, never a guess.

A connected account's consent address is pinned to a one-use state that lasts ten minutes, with a PKCE verifier and the session that asked. The hand-off lasts two minutes and is honoured only for that session, so a consent link sent to a colleague connects nothing. An agent whose manifest names other provider addresses than the organization's registration can't connect through it, because the client secret and the person's tokens would go there.

Mechanism

Encryption

api_server/src/core/crypto.py
{"alg": "aes-256-gcm", "key_version": "02", "nonce": "kZ1vV3mO...", "ciphertext": "7Hq0sL2x..."}
  • Each value is bound to its document. The document's id is mixed in as associated data, so ciphertext copied into another document doesn't open.
  • Each value names its key. Several keys may be live at once, and one is active for writes. Rotating is three steps: add a key, seal everything again under it, retire the other.
  • The stores declare what is encrypted, so the pass over everything misses nothing: values, a model connection's key, a connected app's client secret, a source's headers, webhooks' secrets.
  • What can't be opened is never read as empty. For use it is a 409, unreadable. With no keys at all, the server doesn't start.

A file's metadata is encrypted, and its bytes are not: at rest they are the store's to protect. A database without its keys is a database whose values are gone, so back them up with it.

12 · Certificates and trust

Every node proves itself on every call

There are no shared tokens between the parts. Each is a node: it holds an X.509 certificate that leads to a root kept out of the deployment, and it serves HTTPS with mutual TLS on port 8004. Standard TLS does the handshake and the encryption, and the called node decides what its caller may do.

A node never says what it is. Every other node reads it from its certificate, and TLS proves it.

No token is ever made for kind issuer, by anyone: an issuer certifies only itself. So nobody, an API server taken over included, can enroll a node that others would take for the issuer. The issuer keeps a token's hash, and shows its secret once.

Signing an intermediate, by hand

  1. The issuer makes its key and a request, and logs the request's fingerprint.
  2. The operator carries the request to the offline machine, and signs it with the root tool. The tool takes the name and the kinds from the operator, never from the request.
  3. The operator compares the fingerprint with the one logged, so a request swapped on the way is never signed.
  4. The signed intermediate goes back the same way. After the first, the API server can carry it, and the issuer takes it only if it names a key that waits, is an authority, is in its time, and a root signed it. So the API server can carry an intermediate, but not make one.

Renewal starts 30 days before an intermediate ends, and certificates the last one signed stay valid until they end. No node needs anything, since nodes trust only the root.

Taking a node away

There is no revocation list. A certificate is short-lived, and a node is revoked by not renewing it, so the lifetime on its token is how long a node can last afterwards. A shorter lifetime is a faster revocation, and a higher load on the issuer.
