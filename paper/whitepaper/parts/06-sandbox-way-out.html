9 · The sandbox

Every run in a jail of its own

A sandbox is a container where code nobody trusts runs. A caller hands it a program, input to feed it and a few settings. The sandbox runs the program shut in, passes its output back, and ends it. It doesn't know what the program is for: an agent, a test and a script all look the same to it.

The run is the unit of isolation. No field asks for it. Ten runs of the same program are ten jails, whoever asked for them.

Seven layers

One failing alone doesn't let a run out.

1becoming root, gaining any rightthe container: three capabilities, given up as it starts; no setuid program in the image

Mechanism

The jail, exactly

sandbox/config/jail.cfg · sandbox/src/jail.py

Every run is started by nsjail, Google's process jail, built from its source at a fixed release, from one fixed file in the image. Nothing a caller sends changes that file. Per run, the sandbox adds only the slot's user, the program, its arguments and its environment.

Mechanism

The firewall, and how it is proved

sandbox/config/runs.nft · sandbox/src/jail.py

A run keeps the container's network, so it can reach the proxy on 127.0.0.1:3128. One rule, loaded with nft -f as the container starts, lets the slots' users reach that and nothing else, name lookups included. Where the rule can't be loaded, the container stops. There is no way to run without it.

table inet decentai_runs {
    chain output {
        type filter hook output priority 0; policy accept;
        meta skuid 20000-29999 ip daddr 127.0.0.1 tcp dport 3128 accept
        meta skuid 20000-29999 reject with icmpx type admin-prohibited
    }
}

Before it serves anyone, the sandbox starts a run as every run is started. That run must find itself user 1000, find no /data, and be refused a connection by the firewall. Otherwise the sandbox says why and exits, and it tells no caller it is there until this has passed.

Mechanism

What the container needs

sandbox/config/seccomp.json · sandbox/Dockerfile

Making a jail needs a few things a default container refuses. The container is given them, and the runs never are.

SettingWhy
NET_ADMINto load the firewall rule. The container starts as root holding only three rights. Once the rule is loaded, everything is the platform's user, holding none
SETUID, SETGIDthe most newuidmap and newgidmap may hold, to give each slot a user of its own. They are the only programs in the image holding a right, and only for users 20000 to 29999
the seccomp profileDocker's default refuses making namespaces and mounting, which nsjail needs. This one lets those through and refuses what nobody in the container needs: 31 calls, ptrace, bpf, io_uring and modules among them
systempaths=unconfinedDocker hides parts of /proc, and the kernel then refuses a fresh /proc in a jail. Only the platform side sees the container's own /proc, as a plain user
apparmor=decentai-sandboxon hosts with AppArmor. From Ubuntu 24.04 on, the kernel refuses user namespaces to programs AppArmor knows nothing about. The operator loads the profile once on each host
pids_limitsets how many runs it holds at once: this limit less 1,024, divided by 1,024. So 65,536 gives 63 runs. With no limit, 16
Mechanism

A run's life

sandbox/src/sandbox.py · run.py · programs.py · watch.py

A caller asks, by digest. The sandbox takes a free slot, makes the jail, starts the program, and answers. A refused start leaves nothing behind.

Sandbox:Run:start
{"run": "run-7f3k9q", "program": "sha256:9b1e4c...", "arguments": [],
 "environment": {"GREETING": "hi", "LANGUAGE": "en"}, "pass": "p-2c8d1x..."}
→ {"started": true}

Sandbox:Run:input   {"run": "run-7f3k9q", "data": b"{\"ask\": 1}\n"}
Runtime:Run:output  {"run": "run-7f3k9q", "seq": 1, "kind": "out", "data": b"{\"answer\": 1}\n"}
Runtime:Run:ended   {"run": "run-7f3k9q", "code": -9, "why": "memory"}

A program is one file, named by its digest

The sandbox never reads, builds or verifies what is inside. It fetches bytes from the caller that asked, hashes them as they come, and keeps the file only if the hash is the digest. It then makes it read-only and moves it into place in one step. A file that doesn't match, or passes 1 GiB, is thrown away. A runtime answers only for a program it asked this sandbox to prepare, while it is asking.

However it ends, the end is the same

The jail is ended, and every process in it, however many the program started. Its home, /tmp and /dev/shm go with it, and its pass stops working. The next run in that slot finds nothing of this one. A run ends by itself, or with a why: stopped, memory, caller gone or sandbox stopping.

RuleWhat happens
Whom it servesA call is let in when the certificate's kind is runtime, its scope matches where the sandbox names one, and it is a caller this sandbox serves. Each caller sees only its own runs, and their names are its own
A caller goneOne that hasn't answered for 15 seconds is taken as gone: its runs are ended, since nobody is left to read them, and their connections closed
MemoryAll runs share the container's memory. At 90% of its limit the sandbox ends one run: the largest of the caller whose runs use the most together, so one caller's large run can't push out another's many small ones. It then waits 5 seconds to see what that freed
BackpressureA caller that reads slowly answers slowly. The sandbox then reads the program slowly, and the program waits to write. A hiccup is a pause, never a gap
10 · The way out

One door, and a proxy that decides

A run reaches the network through one door in its sandbox, carried to a proxy on its runtime's side, which decides where it may go. A run reaches nothing else, not even a name server.

Where a connection comes from is proven

The egress knows the sandbox by its certificate, which a run can't be given. A pass works only from the sandbox it was given to.

The firewall is one fixed line

Runs reach 127.0.0.1:3128, and that never changes. They need no addresses of callers, and no name server.

Nothing crosses the network in clear

Between sandbox and egress every byte is inside TLS, the pass included, even when the run asked for plain http://.

The refusal is a status line a program can read, and the header tells the egress's answers from the host's. Each connection is logged: sandbox, agent, host, port, address, whether it was allowed, and bytes each way. It never logs what was sent. When a call ends, the hosts its run reached go on the call's line of the audit trail, with how many connections.

Mechanism

The egress, and its passes

runtime/src/nodes/egress.py

The egress is part of the runtime, on a port of the runtime's own, 8005. It shows the runtime's certificate, so a sandbox's check of the runtime's id holds on this port too. The runtime gives each run a pass and changes what it opens as the run's calls come and go. Passes live in the runtime's memory, and end with its runs.
