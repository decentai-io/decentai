7 · Agents, and how one is approved

An address, a catalog, and one exact release

An agent is what the assistant calls to get things done: a manifest that declares what it may do, keep and reach, and a program that does it. Agents install the way tools do. An address and a credential return a catalog, a person reviews one agent, and approval downloads that release and pins it by digest.

The platform ships with no agents installed. An agent may be written in anything: the program is one self-sufficient file per machine, and nothing of the platform goes inside it. Writing one for a system only your company has is the point: the same contract, the same gates, the same jail.

What was reviewed is what is installed. An install takes the snapshot, never what the address says by then.
Mechanism

A real catalog entry

docs/agents/publishing.md · shared/agent_catalog.py

One JSON document, at any address. This one offers one agent, whose program is a script, so one file serves both machines. The digest and size are of the real program: the small worker in docs/agents/worker-protocol.md, 1,140 bytes.

                      "required": ["name"]},
          "outputs": {"type": "object", "properties": {"text": {"type": "string"}},
                      "required": ["text"]}}]}]
    },

      "x86_64":  {"url": "greeter/1.0.0/greeter", "size": 1140,

A catalog holds up to 100 agents and 8 MiB. A wrong entry keeps its errors beside it and can't be installed, and the rest are still offered. Any https server will do: a folder of static files is enough, and there is nothing to run on the publisher's side.

What pins a release

Saving a source fetches a catalog and nothing else. Approval then names the snapshot that was reviewed:

DigestOverWhat it stops
catalog_digestthe exact bytes of the catalog that was readinstalling what wasn't reviewed. A source read again since is refused: source_moved
a program's digestthe program's bytes, one per machinea swapped file. A download past its size is stopped, and one that isn't its digest is thrown away: fetch_failed
manifest_hashthe manifesta change going unseen: an update is offered when the source's differs
release_digestthe manifest, each machine's program and the sample dataa version coming to mean something else: immutable_version. What a runtime said of one release says nothing of the next

One write says all of it, so a chat never sees a manifest and a program that disagree, and a failure leaves nothing behind. Nothing downloaded is run by the API server. The bytes are stored per organization, by digest, so the same agent approved by two organizations is kept twice, and one's deletion or compromise can't reach the other's. An approval carries what it was approved from:

              "at": "2026-10-31T08:13:00+00:00"}}

The reference is the platform's. agt_ and twenty random characters, minted once per install, and worked out from nothing. Everything outside the agent speaks of it by that reference, and the runtime translates at the door, so a program only ever sees its own id. So two publishers' note agents never meet, and naming your agent after another one opens nothing.

RefusedBecause
source_unreadthe source was never read
source_movedit was read again after the page was shown: review it again
invalid_manifestthe entry has errors, each naming its path
immutable_versionthis version is already approved with another manifest, program or sample data. The same bytes again are a repair
fetch_faileda file couldn't be downloaded, is larger than it said, or isn't its digest

Any of these leaves nothing behind, and an agent already installed keeps running what it had. A private source's credential is kept encrypted, never comes back, and goes to the source's own scheme, host and port alone. A file on another host, or a redirect to one, gets no credential, so a catalog can't hand a deployment's credential to a server it names. A token in an address is refused.

The manifest is the contract

The platform validates a manifest before anything runs, enforces it at every call, and trusts nothing else. A manifest that says less than the code does will stop the code. One that says more will fail review.

A manifest fragment. The agent Note, written in YAML for reading; it reaches the platform as JSON. It connects to nothing, and this one function may list, create and update its own notes, narrowed by notebook.

schema_version: "2.0"
agent: {id: note, name: Note, version: "1.2.5", description: "Your working memory across conversations."}
network:
  hosts: []                                  # the whole of where it may connect
authorization:
  scopes:
    notebook: {type: string, description: "Notebook name.", normalization: lowercase}
resources:
  data:
    - id: note
      label: Note
      binding: {cardinality: many}
      fields:
        - {name: title, label: Title, type: string, storage: keys, required: true}
tools:
  - id: notes
    name: Notes
    description: Saves, reads and finds notes.
    resources: {data: [note]}                # the tool's ceiling
    functions:
      - id: save
        name: Save Note
        description: Save a note into a notebook.
        permission_level: 1
        timeout_seconds: 30
        resources: {data: {note: [list, create, update]}}     # this function's actual reach
        authorization: {scopes: {notebook: {from_input: notebook, required: true}}}
        inputs: {type: object, ...}
        outputs: {type: object, ...}
It declaresWhere it is held
network.hostsat the egress, on every connection (chapter 10). A reviewer reads the list beside the functions. hosts: [] reaches nothing. hosts: any is said once, on purpose, and addresses inside the platform's network stay refused
{from_secret: account.imap_host}a host only the person knows. The field must be plain, so a reviewer can see it, and the host is open only while a call holding that credential runs
permission_level, inputsat the gate
outputsafter the function returns, before anything is shown as fact
resourceson every ask, by operation: list, read, use, create, update, delete. A function without delete can't delete, though a sibling can
secrets, by shapea shape is no access. Which saved credential answers is a person's grant to that slot
llm, credentials, code, watchthe ask is refused unless the function declares it
schedulableread at validation: level 0 or 1, and no model

Inputs and outputs are JSON Schema, deliberately reduced: no $ref, no allOf, no anyOf, depth 5 at most. A schema a reviewer can't read at a glance is one nobody checks. A key the platform doesn't know is ignored in most places and refused inside network, so a mistake in where an agent connects is loud. A version is immutable once approved: every change to a manifest is a higher version.

Beside agents: a person's MCP server

A remote tool server a person adds is not an agent. Its tools run on its server, so there is nothing to jail, and the questions are where the request may go and what the answer is worth. It passes the same gates. Each tool starts at level 3 until its person prices it, what a server says of its tools is data, and a tool that changes comes back switched off. It reaches public addresses only. The Safety page can turn MCP servers off for an organization.

8 · The worker

A program, two pipes, and no standing credentials

An agent's program speaks one JSON message to a line on its standard input and output. That is the whole interface between an agent and the platform. The runtime holds all authority. A worker can only ask.

A worker starts with no credentials and no grants. A function is handed a credential when it asks for one its manifest declared, for the call that asked.

A worker is one run in a sandbox, and there is one run of an agent per chat. The runtime never loads agent code, which is why a hung or crashing function can actually be ended. A worker is disposable at any moment, and what it keeps between calls, a browser left open, is a convenience and never the record.

Mechanism

A real exchange

docs/agents/worker-protocol.md · runtime/src/nodes/worker.py

Requests flow both ways on the same two streams, and each side numbers its own. Three shapes, JSON-RPC in spirit. This session is the program from the catalog above, fed these three lines, with its answers exactly as it wrote them. → is the runtime speaking, and ← the worker.

→ {"id":1,"method":"hello","params":{"protocol_version":2,"manifest":{}}}
← {"id": 1, "result": {"agent_id": "greeter", "version": "1.0.0", "functions": ["greeter.greetings.hello"]}}
→ {"id":2,"method":"invoke","params":{"call_id":"c_9f2","function":"greeter.greetings.hello","inputs":{"name":"Dana"}}}
← {"id": 2, "result": {"result": {"text": "Hello, Dana."}, "status": "success"}}
→ {"id":3,"method":"shutdown","params":{}}
← {"id": 3, "result": {}}

In hello the worker is told the approved manifest rather than reading its own. Inputs reach it already validated, with defaults applied. Its function is greeter.greetings.hello, by its own id, whatever reference the platform gave it. A function that needs something asks, naming its call, while its invocation is open:

→ {"id":4,"method":"invoke","params":{"call_id":"c_7aa","function":"mail.inbox.read","inputs":{"limit":20}}}
← {"id":1,"method":"resources.use_secret","params":{"call_id":"c_7aa","resource_id":"mailbox"}}
→ {"id":1,"result":{"account":"dana@acme.example","access_token":"ya29..."}}
← {"id":4,"result":{"result":{"messages":[...]},"status":"success"}}
It asksAnswered when
resources.use_secret, list_secretsthe function declares that resource and use. As a credential is handed over, a host it names is lent to the call
resources.*_data, *_filethe function declares that resource and operation. A write is held to the manifest's fields, in the agent's own slot
llm.completellm: true, and a person stands behind the call. The stored key never enters the run
credentialcredentials: true, and a person stands behind the call. Values go from the vault to the worker, never onto a card or a record
propose, installa card the person allowed. install needs code: true, and the packages named on a card of this call
askany time. The function's clock stops while the person decides. With nobody behind the call the answer is null at once
show, post, progressat most 5 displays and 3 posts a call. A display is an offer the assistant may decline. A post reaches the model marked as data
Mechanism

What the runtime assumes of a worker

runtime/src/nodes/worker.py · gates/gate.py
  • Its answer is claimed, not believed. The keys only the platform writes (storage_ref, displays, denied, not_permitted) are taken out of what it returned, and a success must fit the manifest's outputs, or the call fails.
  • Its identity is its process. An ask is answered only when it comes from the worker the invocation was sent to. A call id learned any other way opens nothing.
  • A worker that breaks the framing is ended, not accommodated. One line that isn't a JSON object, or passes 2 MiB, ends it. Standard error is its log, never parsed.
  • The runtime owns every clock. Past timeout_seconds, 60 unless declared, a worker is sent cancel, and has 5 seconds before it is ended.
  • Nothing is retried by itself. Ending a worker fails every call in flight with an honest error, because the runtime can't know what a half-run function changed.
  • At most 32 asks are answered at once. Past that a worker isn't read, and waits. Its output waits in the sandbox too, so a flood slows only itself.

A run starts at the first call of its agent in a chat, is greeted within 60 seconds, and is replaced when its program changes. It is retired after 5 minutes idle. Its environment is an allow-list: HOME, TMPDIR, PATH, the browser's path, its proxy with its pass in the address, and the platform's settings for agents, by four prefixes. The model's key and the runtime's settings never reach it.

Honest edge

Two calls in flight on one worker are one agent's code, and nothing on the wire keeps one from asking under the other's id. A worker's process lives between calls, so code that wanted to could keep a value it was handed for as long as the run lasts.
