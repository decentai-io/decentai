Part three

Running and doubting it

How it is laid out, what leaves it, what a taken-over part would get, what is tested, and what isn't proven.

15 · Laying it out

The same nodes, on one machine or across sites

Nothing in a node changes between layouts: only what sits behind each address, and what the operator puts in each identity folder. One API server serves many runtimes, each with its sandboxes. A runtime and its sandboxes are an execution node.

A chat belongs to one runtime at a time

Nobody registers a runtime. The operator starts one and names the API server, and it says it is there every five seconds. That report places chats and shows them to a person. It admits nothing: a runtime's id, scope and labels come from its certificate. A runtime silent for 15 seconds is given no chats, and after 70 seconds it is gone and its chats go free. Each rebuilds from the record on another runtime and hears what it missed exactly once, since every frame is recorded before it is sent.

A runtime keeps nothing, so losing one loses no decision. It holds each chat's state as one document, saved to the API server after every step, and first whenever a call parks.

An organization's own nodes

One deployment can hold many organizations, and an organization's administrators can run nodes of their own. They make an enrollment token, and every node it enrolls carries the organization as its scope and serves it alone. A runtime with no scope is shared. Where its chats run is the organization's setting:

Settings:Nodes:Update
{"placement": "own_only"}
→ {"nodes": {"placement": "own_only"}, "own_connected": ["runtime-4q8w1z"], "moved": 2, ...}
With own_only, nothing of the organization reaches a shared runtime: no chat, no credential, no model key, no code, and no schedule's fire. Checked at the gateway, whatever the runtime holds.

Sandboxes are set aside the same way, by the scope in the token they enroll with, and no setting can widen it. The operator is a role of its own: the administrators of one organization, holding nodes:authority:shared. An administrator of any other organization holds everything in their own, and is still not the operator.

17 · If a part is taken over

What they get, and what stays out of reach

Security that assumes nothing will ever break isn't security. So the question for each part is what an attacker who took it over would get, and what would still be out of reach.

Keeping one agent out of another's data is the runtime's work. The API server decides person and chat, and the runtime names the slot. So a taken-over runtime reaches across agents, within the people whose chats it holds.

The approval hash binds what ran to what was shown against a fault, a restart or a changed input. It isn't proof against a taken-over runtime, which computes and compares it. That is the reason for the checks at the data: a runtime gone wrong reaches only what its chats could reach anyway, and a person with no chat there is out of reach.
