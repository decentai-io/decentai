Chapter 12

Clients

The engine is headless: it serves an API and no page. Three clients use it — a web client, a phone app and a desktop app — and none of them holds authority. Each shows what the Data Core says the signed-in person may see, and asks the Data Core for everything else.

12.1 One API

A client renders a small, fixed set of routes on the Data Core's one published port. POST /app carries every action, named Domain:Controller:action and checked against the caller's policies (chapter 4). WS /chats/{chat_id} carries one live chat. The other routes sign people in, move files and take redirects and webhooks. No client has a route or a permission of its own.

The reason is the threat model. A client runs on a device the platform does not control, and a modified copy can send any request it likes. A client that hides a button does so for convenience, not for safety.

At sign-in the web client sends client: "web" and the phone app client: "native". Each receives the session token in the response body and presents it as a Bearer header. A browser on the engine's own origin that names neither is given a cookie instead.

I-12.1

No client is a security boundary. The Data Core filters every read it serves a client inside the query, and resolves every action a client sends again from the session on the server. A modified client gains nothing an honest one lacks.

12.2 The web client

The web client is one build of static files, pointed at an engine by one file read at run time. It is an Angular 20 single-page application, served by its own container, by any static host, or from inside the desktop app. The file, assets/config.json, says {"engine": "https://api.example.com"}; the container writes it from ENGINE_URL as it starts. The service worker never caches it, so changing it moves every browser on its next load.

An address the person entered comes first, then config.json. Failing both, the client tries the page's own origin, for a reverse proxy that serves the engine beside the app. It accepts that origin only if GET /auth/setup answers JSON carrying setup_required, which only an engine does; otherwise the Connect screen asks.

The token is stored with the engine that issued it and dropped when the address changes, so one engine's session is never offered to another. A browser cannot set headers on a WebSocket handshake, and a token in the URL would be written into every log on the way. So the chat socket offers the token in its subprotocol list, after the name decentai.bearer. Because the engine is on another origin, the browser enforces CORS_ALLOW_ORIGINS: the Data Core answers preflights only for the origins listed there.

The chat page

A chat is shown as turns: a person's message and what came of it. Socket events carry sequence numbers. On reconnecting, the page replays what it missed from the Data Core's event log and holds live frames until the replay is done, so no event is applied twice or out of order. If the log has moved past where the page stopped, the page reloads the chat instead.

A turn that did work has a work block: the assistant's plan, each item with its status and what the trace proved for it (chapter 5), and the calls made, grouped by agent. Cards appear in the thread where work waits (chapter 6), and each is answered once. Read-aloud speaks a reply in pieces, so the first sentence plays while the rest is prepared.

12.3 The phone app

The phone app is a remote control: it keeps a person in the loop away from a desk. It is an Expo (SDK 57) application in React Native 0.86 for iOS and Android, and connects to any DecentAI server by address. It covers chats, a Cards list of everything waiting for the person, schedules, background work, notification settings and the switch that stops everything of theirs. Agents, credentials and organization settings are set up in a browser.

The first screen takes a server address, an email and a password. Signing out deletes the token and keeps the address. React Native, unlike a browser, lets a socket carry headers, so the chat socket sends the token as an Authorization header. Push notifications go through Expo's push service: the app registers its push token with Settings:Notifications:Subscribe, and tapping a notification opens its chat. The phone must reach the server: localhost on a phone is the phone, so a server on a person's own computer needs a tunnel or a network address.

12.4 The desktop app

The desktop app is the released web client in a window of its own, pointed at a server or at an engine it runs locally. It is a Tauri 2 shell for Windows and macOS. On first opening it asks once: connect to a server, or run DecentAI on this computer. Either way the shell itself answers assets/config.json, with the server's address or http://localhost:<port>.

The page's origin is http://tauri.localhost on Windows and tauri://localhost on macOS. No web page can claim those origins, which is why the engine's default CORS_ALLOW_ORIGINS lists them. The page gets none of the shell's native commands, so nothing rendered in a chat can stop or uninstall the engine. Links other than sign-in windows open in the person's browser.

Running DecentAI here

The app installs nothing itself: a launcher container does the work, and trusts only a signed release. The launcher carries its own docker compose and is handed the container engine's socket — Docker where it is running, otherwise Podman — so it behaves the same on Windows and macOS and is updated by pulling an image. It starts the engine's seven services as Compose project decentai-desktop, apart from a developer's own decentai stack, from images pulled by digest. Keys are made once. A first run that stopped half way reuses them, because keys made twice leave a database nobody can read. The settings are those of section 13.4.

A release is release.json (schema 2.0) with an Ed25519 signature beside it. It names by digest the engine's images, mongo, the launcher and the bundled web client, and the oldest launcher that understands it. The app reads it to choose the launcher, and the launcher reads it again before installing. Both believe it only if it is signed by one of the keys the launcher ships with; an unsigned file from one's own build is installed only when explicitly allowed. An update pulls every image first, copies the database, then switches releases. If the new stack is not healthy, the previous release returns with the copy restored.

I-12.2

The desktop app runs only images named by digest in a release file whose Ed25519 signature verifies against a key it ships with. Otherwise, whoever could put a release file in front of an install could put their own software on the machine.

Chapter 13

Deployment

The platform is one image per process, configured entirely by environment variables: a laptop, a virtual machine and a cloud differ in values, never in code. TLS, public hostnames and proxies belong to a deployment, and the recipes in decentai-deploy supply them.

13.1 What is deployed

The engine is three images and MongoDB 7, and it publishes one port. The images are the Data Core's, which also runs the node issuer; the AI Runtime's, which also runs the Execution Sandbox; and speech. Together they make seven containers on the three networks of chapter 2. The one published port is the Data Core's, plain HTTP, 4280 by default. The web client is served separately.

An execution node dials the Data Core's /nodes/link over the public address people use, and nothing dials a node (chapter 8). So moving agent code to another machine opens no inbound port; that machine only needs to reach the engine's HTTPS address.

single-host needs a Linux host with Docker Engine and Compose 2.24 or later, two DNS names (api.<domain> and app.<domain>) and ports 80 and 443 open; Caddy handles the certificates. Its setup script runs inside the Data Core's image, so the host needs no Python. Two names keep the engine's origin apart from the app's, as the engine is tested; LAYOUT=path serves both under one name.

With ROLE=core the server runs the Data Core's side and writes a node bundle once: the Data Core's public key and address, the node's sandbox secret and the node authority's private key. The node recipe on the other machine unpacks the bundle and deletes it, and it is deleted on the core too, so the authority's private key exists on the node alone. The node publishes no port; once linked, it appears on the Data Core's Nodes page.

13.3 Two VMs on AWS

cloud-vm/aws is Terraform for the whole deployment: a VPC with one public subnet, two EC2 VMs (Ubuntu 24.04, encrypted disks), an Elastic IP for the core, Route 53 records when a hosted zone is named, and daily disk snapshots, the last seven kept. The core admits 80 and 443; the node admits nothing. SSH is off by default, and the VMs are reached through Session Manager.

The VMs need no git: each first boot copies its recipe from a private S3 bucket and runs it. The node bundle travels once through an encrypted SSM parameter and is then deleted. Both VMs require IMDSv2 with a hop limit of one, so no container can reach the VM's instance role. With ecr_mirror = true, images not yet public are pulled from ECR in the account.

I-13.1

A deployment publishes one door: the Data Core's port, or the TLS terminator in front of it. The database is on an internal network that only the Data Core and the seeder reach. An execution node publishes nothing, because it dials the Data Core and is never dialed.

13.4 The desktop's local install

The desktop install (section 12.4) is the one-computer topology with every edge turned inward. The Data Core listens on 127.0.0.1 only, with nothing in front of it, and CORS_ALLOW_ORIGINS holds the app's two origins alone. No setup code is asked (SETUP_CODE=none), since nobody else can reach the address, and sign-up is closed. No email is sent: invitations become temporary passwords shown once, and the launcher resets a forgotten password. Speech fetches no model until an administrator turns it on. Reaching the install from a phone takes a tunnel the person sets up.

13.5 The configuration surface

Each process receives only the secrets it needs. The settings file, config/deploy.env, goes whole to the Data Core and the seeder. The node's sandbox secret goes only to the runtime and its sandboxes, and the authority's private key only to the node issuer. The runtime never sees the database password, the encryption keys or the Data Core's private key. The settings that matter most:

Keys are generated, never chosen, and no generator writes its output to disk. Encryption keys rotate by appending a version: new writes use it, and a re-encryption tool rewrites stored values until the old version can be dropped. A ceiling on trust levels is deliberately not a setting: trust belongs to a chat, bounded by what its person may do.

I-13.2

A database is readable only with the keys it was written with. Setup and update scripts make each key once and keep it thereafter. They add a key a newer version needs, and never replace one that exists.

13.6 Volumes and backups

A deployment is its settings, its database, and its file and package volumes; everything else is rebuilt.

mongo_data
the database: identities, chats, records, encrypted values. Back up.
uploads_data
file bytes, with the local store. Back up.
agent_packages
approved agent packages, the only copy the platform controls. Back up.
the settings
the keys: without them stored credentials are unreadable and the node authority is lost. Back up.
the rest
caches, speech models and the node credential, all rebuilt or fetched again.

single-host's backup script writes all four, taking a mongodump archive while the database runs. On AWS the disk snapshots come in addition, not instead.

13.7 Updates

A release is a version tag on a commit whose tests passed. The release workflow builds the three images for Intel and ARM, publishes them to ghcr.io/decentai-io and names each digest in a GitHub release. The web client is released separately. Recipes pin both versions and pull; they never build.

An update runs the new seeder first, while the old code still serves, then rolls the services. A seed adds collections and actions and drops no data, so older code runs against a newer database and going back is naming the previous version. As it starts, each version removes indexes its schema does not declare, and policy actions its catalog no longer has. A node whose protocol differs from its Data Core's is refused, so a core and its nodes are updated together.

Chapter 14

Verification

Each property this paper states is meant to be checked, not believed. The checks are automated suites that use the platform as a person, an agent or an attacker would; a hostile agent run in the deployed containers; and tests that hold the documentation to the code.

14.2 A scripted model

Runtime tests run real agent code in real worker processes against a scripted model, which returns replies written in advance. A test must give the same result on every run, which a real model does not, and the claims under test concern what the platform does with whatever the model proposes. The simulator answers the Data Core's services in memory; agent authors use it too. The spanning suite closes the gap the simulator leaves. In its full-stack test a person's socket reaches the Data Core, which attaches a real runtime process, and the runtime calls back over /app under the chat's delegation. Only the model is stubbed.

14.3 An agent written to escape

The live suites install an agent that is hostile on purpose. Each of its functions attempts one escape: read the runtime's settings, write into its own package, signal the runtime, connect past the proxy, resolve a name directly, open an unused socket family, ptrace, create a namespace. A test passes only if the attempt is refused. Beside each refusal a positive control checks that ordinary work still functions, since a sandbox that refused everything would also pass. A second hostile package attacks at build time.

I-14.1

A green confinement run has run the hostile agent. The live suites skip everywhere but the container stack, and the CI job fails when either passed nothing. So a run in which every test was skipped for want of a kernel feature cannot be reported as a pass.

14.4 Documentation held to the code

Five tests keep the documentation, from which this paper is distilled, in step with the code. Every relative link reaches a page and a heading on it; every repository path a page names exists; every documented setting is read by some code, and every example setting is documented; and the published list of actions is exactly what the Data Core's catalog holds today. These tests check what a page points at. Whether a sentence is true remains for a reader to verify.

14.6 What is not evaluated

  • Model behaviour. No test calls a real model. The tests show that a proposal cannot pass the gates; they do not measure whether a model resists injected text or chooses well.
  • Performance and scale. No overhead is measured, nor behaviour with many organizations, chats or concurrent schedules.
  • The kernel. Confinement results hold on the kernel tested; a kernel flaw is a way past every layer.
  • The clients. The web client's suite was not part of the reported evaluation, and the phone app has none.

15.2 What is not built yet

No release has been published at the time of writing. The decentai-deploy recipes pull released images, so until a release exists they run images of one's own (or the ECR mirror, on AWS). Recipes for Azure, Google Cloud, Kubernetes and marketplaces are planned and absent. The desktop install listens on 127.0.0.1 only, sends no email, and does not carry over installs from the earlier monolithic app. The phone app configures only its own use.

15.3 Open questions

The October 2026 review raised design questions it did not settle: choices, not defects, where either answer may be right. They are published with the code as a list, each naming the function it concerns and whether it was reproduced or found by reading. Appendix

Glossary

The words this paper uses for one exact thing.

Action — one operation the gateway dispatches, named Domain:Controller:action; what a policy grants.

Agent — an approved program: a manifest and code in a git repository, installed as one exact commit.

AI Runtime — runs each chat's assistant, the executor every call passes, and the egress proxy. It has no database.

Audit trail — the append-only record of what the platform allowed: calls, approvals, credential reads, installs, grants, stops.

Card — something in a chat that waits for a person: an approval of one exact call, a question, code to allow, a login.

Data Core — the engine's one door: identity, policy, the vault, the data layer and the relay; the only part that reaches the database.

Delegation — a short-lived credential minted per chat and bound to one node, under which the runtime acts for the person within 41 actions.

Evidence — tables, charts and files the platform shows beside a reply, rendered from stored results the trace proves exist.

Execution node — one AI Runtime and its Execution Sandboxes, admitted by an authority's key. It dials the Data Core and is never dialed.

Execution Sandbox — a container where agents' workers run, started by its spawner; it reaches only its runtime.

Function — one operation an agent's manifest declares, with input and output schemas and a permission level.

Gateway — POST /app, the one route every action goes through and where permission is checked.

Grant — permission to use something: a policy allowing an action, an agent granted to a person or group, a credential lent to an agent.

Launcher — the desktop app's container that installs and updates the engine on one computer from a signed release.json.

Lease — which node holds an active chat, numbered and renewed by heartbeat; a call with an old number is refused.

Manifest — an agent's contract: its functions and levels, records and files, credential, hosts and dependencies.

Permission level — 0 to 3 on a function: a read, an ordinary change, a wider change, an outside action (one that leaves the platform or cannot be undone).

Plan item — one entry in the assistant's plan, kept by the platform with its status and the references offered as proof.

Proxy — the runtime's egress proxy on port 8002: a worker's only way out, open to the hosts its agent declared.

Record — what an agent keeps for a person, in its manifest's shape, with plaintext keys and encrypted values.

Skill — a short instruction an organization wrote for the assistant, pulled into a chat when the task calls for it.

Trace — what the assistant actually ran in a chat; evidence and plan proofs are checked against it.

Trust level — 0 to 3 on a chat, set by its person: a function at or below it runs unasked; above it, it waits for a card.

Worker — the process an approved agent's code runs in, as its own user, fenced to its own files.
