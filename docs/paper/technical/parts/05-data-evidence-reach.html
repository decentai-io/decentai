Chapter 9

Secrets and data

Everything a person owns lives in one database and is shared by one mechanism. Secrets go further: their values reach an agent's code for one call, and never a person or the model.

9.1 The data layer

The Data Core keeps all its state in one MongoDB database of 45 collections, each declared with its validator and indexes in one schema. At start it creates what is missing, enforces every validator and drops any undeclared index, so the database is exactly what the code says.

The collections cover identity and access (12), chats (8), agents (5), the data layer (6), connections (3), execution nodes (4), reach (5) and evidence (2). Thirty-three carry org_id; the rest hang off a row that does, or belong to the deployment rather than to a tenant.

The six data-layer domains share one document shape. resource_ref names the document, resource_id is a category label many documents share, and owner maps the groups and users who may see it. keys holds plaintext metadata that can be searched; values holds the encrypted payload, which cannot. A document holds at most 50 entries and 10 MiB of values.

Visibility is a filter, not a check. Every read builds its query from the caller's organization, the domain and the owner map, so it cannot match a document the caller may not see. A check after a lookup can be forgotten; a filter inside the lookup has to be removed on purpose. Even the Everyone share resolves within the reader's own organization.

Two rules govern writes. Nobody may share beyond their own groups and the peers in them, and only the creator, the steward, may edit, re-share or delete. A per-domain escape grant lifts both rules, and stewardship can be transferred. One sharing engine applies this to secrets, records, files and skills (PERSONAL) and to model connections and agent sources (INFRASTRUCTURE).

9.2 Encryption at rest

Every encrypted field is sealed with AES-256-GCM, using a 32-byte key and a fresh 12-byte nonce, and records its key version. The document's _id is the associated data, so a ciphertext copied into another row fails to open. It binds to the id rather than the owner, because owners change.

Keys come from SECRET_ENCRYPTION_KEYS, a list of version:base64-key pairs. SECRET_ENCRYPTION_ACTIVE names the version for new writes, by default the highest. Mixed version widths (1, 2, 10) are refused, because versions compare as text and a stale key would become active. Without keys the Data Core does not boot.

Rotation is three steps: add a version and restart; re-encrypt everything, after a --check pass that only counts; retire the old key. The re-encryption tool asks each store for its own encrypted fields, because a field a hand-kept list misses is lost for good when its key goes.

A value whose key is missing shows as unreadable, so one bad row does not blank a page. At use it fails loudly, with a 409 that says how to fix it: an agent acting on an empty credential is worse than one that stops.

I-9.1

A sealed value opens only in the document it was written for, under a key version the deployment still holds. Nothing falls back to a default key or returns partial plaintext.

9.3 Credentials

A credential is a secret saved against a definition, which lists its fields and says which are encrypted or required. Definitions are derived from manifests, each in a namespace private to one agent (agt_<ref>__<slot>), so a category names exactly one approval. If names were shared, any repository could declare the same fields and read what was stored under them.

Definition versions are immutable. After an agent update, a credential moves to the new version only if that version asks nothing new of its owner. Otherwise it is marked outdated and refused at use, with a sentence saying what is missing.

The creator is a credential's steward. Sharing lets colleagues' chats use it, not edit it. A grant points one saved secret at an agent's declared slot of exactly the same shape, so several agents share one key and a rotation stays one act. At use, the Data Core takes the chat's binding, else a grant to that agent, else the person's default, else the only visible instance. If several remain, it reports an ambiguity rather than guessing.

A worker starts with no credentials. When a function asks for its slot, the host checks the declaration and calls the Data Core as the chat's delegation. The Data Core decrypts, writes secret.use to the audit trail, and returns keys and values together, because a password is of little use without its hostname. The values reach only the worker's memory, and the proxy opens the credential's host for that one call.

One gap remains: a warm worker could keep a value between calls. An access token's expiry bounds that risk; nothing bounds it for a typed key. This is why agents are read before they are approved.

I-9.2

A secret's values leave the Data Core only through two runtime-only operations, Secrets:Secret:Use and Secrets:Credential:Resolve, and only toward the worker of a function that declared the slot. No read by a person returns them, and the model is never on the path.

9.4 Connected apps

Some credentials come from an OAuth sign-in, and the platform, not the agent, runs that flow. A definition's oauth block names the provider, its addresses and its scopes. The organization holds one client registration per provider, with a write-only client secret, and the registration pins the provider's addresses. An agent that names other addresses cannot connect, because the client secret and the person's tokens would reach its server.

Secrets:Oauth:Start writes a single-use state row, valid ten minutes, holding a PKCE verifier and the browser session that asked. The provider returns to /oauth/callback, which spends the state, requires the same person in the same session, exchanges the code, and creates or refreshes the credential.

The web client's session cannot ride in a popup, because the client runs on its own origin. The callback therefore parks the code behind a two-minute, one-use hand-off, posted only to the PUBLIC_APP_URL origin. The web client or phone app spends it with Secrets:Oauth:Complete under its own session, where the same-person check runs.

At use, the Data Core first refreshes an expiring token. The agent receives the account and an access token; the refresh token never leaves the Data Core. If the person revokes access at the provider, the credential is marked needs_reconnect.

9.5 Records and files

Records (agents_data) are what an agent keeps for a person, such as a watcher's memory of what it has seen. Each follows a shape the manifest declares, which a person's writes must also meet. A person may write only where the manifest's user_access allows, and may otherwise read and delete. Exports leave out fields marked secret.

An agent reaches records and files only in its declared slots; anything else answers as nonexistent. The exception is a ref the call was handed, in its inputs or the person's answer, which it may read but not write or delete.

Files hold bytes as well as a document. Only an upload creates one, because a storage location taken from a caller could point anywhere. The storage id is derived from the bytes, name, purpose and uploader, and the bytes go with the last document that refers to them. Uploads are capped by MAX_UPLOAD_MB (default 25).

FILE_STORAGE_PROVIDER selects local disk, s3 (or any S3-compatible store), azure_blob or gcs. Each document records the connector that wrote it, so a store the deployment has left can still be read. Each connector refuses a path that climbs out of its root. Memories, chats and execution nodes sit outside this layer on purpose.

9.6 What leaves a deployment

Nothing goes to DecentAI's makers. Data leaves only by these routes, each decided by a named role. A chat's messages go to its model provider, and with its model key and granted credentials to the execution node that holds it; Own nodes only keeps an organization off shared nodes. An agent's traffic goes through the proxy to its declared hosts. Sign-ins go to OAuth providers, MCP calls to a person's own servers, notifications through push services and the mail server, and outbound webhooks to subscribed addresses. Speech goes to a provider only where an administrator chose one. The vault, the trail, files, records and chats stay in the deployment's own storage.

Chapter 10

Evidence, monitoring and audit

The model's words are its own. Whatever the platform asserts about a turn comes from records it wrote: what the chat saw, what was allowed and done, what the processes did, and what the models used.

10.1 The activity stream of a turn

A chat keeps two logs in ai_chat_events. The inbox holds what the assistant must absorb: messages, finished jobs, fires and webhooks. Each event is numbered and written before the assistant hears it, so a session rebuilt after a crash resumes from its bookmark. The outbox is the audience's replayable log of frames such as message_created and activity.

An activity line has a kind, such as call_started or call_finished (with status and duration), and the lines of one call share its call_id. The Data Core validates each event as it records it; a malformed one is lost from the replay, not from the live stream. Screen frames are never recorded.

10.2 The audit trail

The audit trail, ai_audit, is append-only and written at the Data Core's chokepoints. Each line holds the event type, who acted for whom, the chat, function and resources, details and time. The Data Core records its own acts, such as secret.use, llm.use, approvals, grants, schedule.* and work.stopped. Any other gateway action that changes state, refused or not, becomes platform.action with its outcome: success, denied or failed.

The runtime may write exactly one type, execution: the agent, function, levels, an outline of the inputs, the outcome, the duration and the hosts the proxy counted. With only that type, the runtime cannot forge an approval or a credential read.

The trail is a witness, not a gate. An append is tried twice; a line the database refuses goes whole to the error log at CRITICAL, and the act still happens.

A person reads their own trail (ai:audit:list), also shown per chat; the organization's whole trail needs ai:audit:list_all. Lines outlive their actors. No secret value is written, but an agent's error text and the model's proposed inputs are kept as they came.

I-10.1

Nothing through the gateway edits or deletes an audit line. The runtime adds only execution lines; every other type is the Data Core's record of its own act.

10.3 The evidence behind a claim

Evidence (chapter 5) rests on these records. While a plan item is active, the storage ref of each successful call and the id of each finished job attach to it, and the model may cite only those. An item marked done without them shows as unverified. Tables and charts are rendered from the rows stored in ai_chat_storage, so no value is retyped.

10.4 Monitoring

Monitoring shows what the agents' processes did. The runtime and each Execution Sandbox write JSON lines to their own folders, because no container may read another's. The lines record workers starting and ending, logs, processes, memory and connections. A connection line holds the host and resolved address, whether it was allowed and reached, the bytes each way and the duration, but never contents: the proxy does not open TLS.

Each writer keeps at most 64 MiB, and a failed write never fails what it records. The Data Core asks each connected node a monitor question over its link and shows each organization only its own agents' lines.

10.5 Token accounting

Every model answer a chat receives becomes one llm_usage row, kept for 396 days, with its purpose, connection, model, tokens and duration. The organization, person and chat come from the delegation, never from the runtime.

Providers count cache tokens differently, so the runtime normalises every answer into input (uncached), cache_read, cache_write, output (thinking included) and reasoning. The cache share, cache_read / (input + cache_read + cache_write), measures how well prompt caching works.

Rows are sent in batches of at most fifty, which no beat waits on. Cost is an estimate at the catalog's prices; an unpriced model's tokens appear as unpriced_share, never as a cost.

10.6 Package checks and health

A sandbox proves a package before it runs it. It checks the bytes against their digest and the manifest against the approved hash, builds the dependencies, then starts one worker whose greeting proves the package loads: the verification start. The Agents page shows Preparing → Ready or Failed, and a failure is remembered until the approvals change.

Health has three routes. The Data Core's /healthz checks liveness only. Its /readyz pings MongoDB and answers 503 without naming the database, because anyone may call it. The runtime's only HTTP route is /internal/health/live on port 8001.

Chapter 11

Time and reach

A chat keeps working while nobody watches. A clock wakes it, outside systems may call it, and when something needs a person the platform finds them. Every path has a limit, and one switch stops them all.

11.1 Schedules

A schedule (a row in ai_schedules) wakes a chat at a set time, in one of two modes. A third kind of wake belongs to the assistant alone:

  • A wake delivers a note, such as "morning brief", and the assistant decides what the moment means.
  • An invoke runs one function the manifest marks schedulable, at level 0 or 1, with fixed inputs and no approvals or model. It wakes the assistant only when the result's wake_field is non-empty, so an empty five-minute sweep costs no model call.
  • A sleep is the assistant's own one-off wake: one per chat, at most a day ahead, not shown on the Schedules page. A longer wait must be a schedule the person can see and stop.

A time is given as at (ISO 8601, in the person's time zone), delay_seconds, every_seconds (at least 60) or a five-field cron. A chat holds at most 50 rows.

The clock is the Data Core's, so a row fires once however many nodes hold its chat, and even when none does. Every five seconds the clock places each due chat on a node. It claims the row with a conditional write that holds only if the due time is unchanged, then sends a signed fire over the node link. Four timing rules follow:

  • A period counts from when the row was due, not when it ran, so an hourly row stays on the hour.
  • An overdue row fires once and rejoins its schedule. A Data Core that was down replays no backlog.
  • The next run comes at least 60 seconds after the last fire, so a miscomputed row cannot spend a model turn on every tick.
  • A row never runs twice at once. One fire may wait; later ones fold into it as merged, and a pause drops it as skipped.
I-11.1

The Data Core fires each due row once, under a conditional claim. No node decides when, and no outage becomes a burst of missed runs.

11.2 Webhooks in

An inbound webhook lets an outside system wake one chat with typed data. Each webhook (whk_…, at most 25 per person) has a name, the person's instruction, up to 40 typed fields and one standing chat, which every event wakes and which keeps its plan between events. Its secret (dws_…) is shown once. It is sealed, not hashed, because checking an HMAC needs the secret itself.

I-11.2

What an outside system posts reaches the assistant as data beside the person's own instruction, never as an instruction.

11.3 Webhooks out

An outbound webhook tells a person's own system that something happened in a chat. A person may subscribe up to ten https addresses to approval.waiting, reply.ready, run.finished and run.failed; card and reply events are queued only while the chat is closed. A body carries the event, the chat, a line, a link and the time, and the reply's text only on request. It never carries a secret or the conversation.

JSON bodies are signed as inbound calls are, with the subscription's sealed dss_… secret; Slack and Teams receivers check no signature, so their bodies are unsigned. Each attempt has a 10-second timeout and follows no redirect. A timeout, a 5xx, a 408 or a 429 is retried with a growing delay, from one minute to six hours, for one day. Twenty failures in a row pause the subscription.

Every address is checked when it is subscribed and again before every send, and refused if any DNS answer is off the public internet, including IPv4 carried inside IPv6. Anyone may subscribe, so a notification must not become a route to the database or a cloud's metadata address. The connection itself is made by name, so DNS rebinding between check and connection remains a known limit.

11.4 Notifications

The notifier (chapter 3) pushes to every subscribed device when a card opens or the assistant answers in a chat no browser of the person has open, and emails only if no push reached anyone. It runs on its own thread, so no turn waits on a push service. Browsers get web push signed with the deployment's VAPID key pair, which a push service holds for up to 24 hours; phones get Expo push. A device the service reports gone is dropped.

Email goes at most once per chat every ten minutes and answer pushes at least two minutes apart; cards are not spaced, because someone is waiting. A card names the agent and step from the approved manifest. Because the text passes through outside services, a person may turn Say what happened off, and an organization may require that of everyone; the notification then says only that something is waiting.

I-11.3

No push and no outbound delivery goes to an address that resolves off the public internet. The check runs when the address is registered and again on every send.

11.5 Stop everything

The stop at the top of every page (AI:Switch) ends all of a person's work without relying on anything to agree. It acts in a fixed order:

  1. The person is marked stopped. From then on nothing of theirs is placed on a node and no key is minted, whether a message, a schedule or a webhook asks, and their webhooks answer 404.
  2. Every chat a node may be serving for them is killed with stop and force, with ten seconds to record what it did.
  3. Every delegation of theirs is deleted, so a process that ignored its end can read no credential, key, record or file.

The stop is recorded as work.stopped. Resuming (work.resumed) is the person's own act and places nothing on a node: a chat returns when it is opened or a schedule falls due, and a schedule due during the stop fires once. No runtime can lift the stop, so stopped work cannot restart itself. Stopping one chat is narrower: it ends what is running but sets no lasting stop, and its schedules keep firing.

I-11.4

While a person is stopped, no chat of theirs is placed on a node and no delegation is minted for them. Work already running loses its keys.
