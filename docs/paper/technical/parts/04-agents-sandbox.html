Chapter 7

Agents

An agent is a folder in a git repository: a manifest that declares everything it may do, keep and reach, and Python that does it. The platform reads the manifest without running the code, an administrator approves one exact version of both, and from then on every call is held to the stored, approved manifest — never to anything the running code says about itself.

7.1 An agent is a package

Nothing about an agent is registered elsewhere or found by convention. The folder holds the manifest, which is the contract; the agent's entry point, which returns its tools; one class per tool, with one asynchronous method per function; a README written for the reviewer; and, optionally, sample records and files a person can load in one click. A function returns a result and a status, success or error; anything else, an exception included, becomes an error result.

At approval the folder is packed canonically: files sorted by POSIX path, mtime and owner zero, mode 0644 or 0755, PAX tar, gzip level 9 with a fixed header. The package digest is sha256: over the gzipped bytes, so one commit always gives one digest and any changed byte gives another. A package holds at most 5,000 files and 64 MB uncompressed, and no symbolic link.

7.2 The manifest

The manifest has seven top-level blocks: schema_version (exactly "1.0"), agent, implementation, network, the optional authorization and resources, and tools. Figure 7.1 is the Gmail agent's, condensed to the lines that carry the design.

Four ideas carry most of the contract. Resources appear twice. The tool lists what its functions may touch at all, and each function maps resource ids to the operations it performs (list, read, use, create, update, delete). A call's resource object is built from the function's map alone, so send cannot delete a draft although a sibling can. Fields are keys or values. Keys are plaintext, scalar and filterable. Values are encrypted at rest, may hold objects, and in a secret are never shown to a person again. Hosts are names, *.name, name:port for protocols other than the web, {from_secret: slot.field} for a host only the person knows, [], or any. Scopes name a dimension a grant can narrow, such as Note's notebook, bound per function to a top-level input with from_input.

The permission level is a price, not a permission. The platform checks only that it is 0–3; the reviewer judges whether it is honest. At the standard chat trust of 1, levels 0 and 1 run and levels 2 and 3 raise a card.

7.3 Validation

One validator runs when a source is read, when an agent is installed, and when the runtime and each sandbox load it. It returns errors, each naming its path (tools[0].functions[2].inputs: …), and never raises. The rules worth naming:

  • JSON only. An unquoted YAML date, a non-text key, NaN, or nesting past 32 levels is refused first, because approval hashes the document as JSON.
  • Ids. agent.id matches ^[a-z][a-z0-9_]{1,31}$; secret ids are at most 34 characters and data or file ids 94, so <ref>__<id> fits the stores. agent, close, id and logger are taken by ToolBase.
  • Bounds. At most 16 tools of 25 functions; at most 50 hosts, lowercase names, never an address, scheme, path or bare *. No network block, no approval.
  • Schemas. A closed JSON Schema subset, object root, depth at most 5; $ref, allOf, anyOf, oneOf, not and conditionals are refused, because a schema a reviewer cannot read at a glance is one nobody checks.
  • Storage. A secret or object field in keys is refused; a from_secret host must name a string kept in keys, so where an agent connects stays visible.
I-7.1

Every component judges a manifest with the same validator and the same fingerprint function, so no two parts of the platform can disagree about what an agent declared.

7.4 Sources and catalogs

An administrator saves a git repository on Agents → Marketplace. The Data Core fetches it at one commit, depth 1, reads decentai-agents.yaml at its root and validates every manifest it names. A catalog lists 1 to 100 entries, each an id and a path and nothing else: what an agent is called is its manifest's to say. The whole catalog is refused if an entry's id differs from its agent.id, a path leaves the repository, or anything is a symbolic link. A manifest that breaks a rule refuses only its own agent, which is listed with its reasons. Reading a source never executes its code. A source belongs to the organization that saved it.

7.5 Review and approval

The review shows what the manifest declares: dependencies, levels, flags, scopes, secrets, data, files, hosts, and the README up to 20,000 characters. An administrator holding agents:agent:install approves the agent by name, and the install works in a fixed order:

  1. It fetches the commit whose catalog the page showed. If the source was read again since, the request is refused (source_moved, 409) and the agent must be reviewed again.
  2. It validates again, and refuses the same version with a different manifest (immutable_version).
  3. It derives secret slots private to this approval, and writes the row with manifest_hash: SHA-256 of the canonical JSON, keys sorted.
  4. Only then does it pack the folder and store it under (organization, digest). If that fails, or the same version arrives with other bytes, the row is put back as it was.
  5. It pins package_digest, grants the installer, reclaims unpinned archives, audits agent.installed, and marks the row preparing.

No runtime is contacted; whether the code loads is the node's own report (§8.3). Archives are kept per organization so that one organization's deletion, retention or compromise cannot reach another's code. Deduplication happens on the node instead.

I-7.2

An approved version names exactly one manifest hash and one package digest. Nothing of an agent runs before an approval names it, and a version is never approved again with other content or other bytes.

7.6 Two names: refs and qualified ids

The author's agent.id decides nothing on the platform. At first install the platform mints a ref, agt_ and twenty random characters, derived from nothing, so nobody can predict one or compute another install's. It is found again at every update by organization, source and catalog id, so an update keeps the agent's records and grants. Everything outside the package speaks the ref: grants, the collections agt_…__draft, secret slots, function names, cards, the trail. Only the manifest lookup and the worker call translate it back, so the code only ever sees gmail. Naming an agent after another gives it nothing of that agent's.

A ref cannot be typed, so each install also gets a qualified id for people and policies: the bare author id when it is free in the organization, else <source>__<id>. It is assigned once and keys nothing, so a later install cannot relabel it.

7.7 Grants, scopes and the chat

Grants are rows keyed by the agent, not statements in IAM policies, because an agent's functions appear, change and vanish with installs, and names written into authored policies rot. An uninstall deletes the agent's grants and credential grants with it. A grant has an owner (up to 50 groups and 50 users), functions ("*" or up to 200 tool.function names) and constraints, the values each scope may take. Grants are allow-only: absence is denial.

On first install only, the install writes the smallest grant that is obviously right: the installer's groups and the installer by name. A repair leaves grants alone, so access arranged since is never undone. Wider access is edited on the agent's Access tab. "*" follows the manifest as it grows; a list keeps a new function closed until someone opens it. At call time the executor reads each scope's value from its input, normalizes it, and holds it to the grants; a constrained allow does not hold for a call that gave no value. Credentials follow the same rule: a saved credential reaches an agent's private slot only through a revocable credential grant that a person writes.

A chat's contract joins three filters: the organization's installed agents, the grants that reach this person, and the chat's enabled_agents. A person's default may name only installed agents, and a chat may narrow it but never reach past it. An agent with no function left after the join is absent from the chat.

I-7.3

A person reaches a function only through a grant row on that agent and a chat that enables it. A chat's list can narrow what a person may use and can never widen it.

7.8 Versions and updates

A version is immutable in its manifest and its code; every change, a sample sheet included, is a new agent.version. An update is offered only for agents whose own manifest changed, and taking it is a new approval. Credentials saved under old shapes follow where that asks nothing new of their owners. At its next call the runtime sees the new digest and retires the old worker. A call still in flight there ends with an honest error and is not retried, because nobody can know what a half-finished call changed. A renamed agent.id is a different agent, which no installation follows.

7.9 What agent code is given

The SDK, decentai_sdk, has no dependencies, is installed into every agent environment, and is the only platform code an agent may import. call carries no identity of the person and no model key. A refusal raises ResourceDenied with the reason in words.

call.inputs
Validated against the manifest, with defaults applied, before the code runs.
call.resources
Records (list_data … delete_data), files (read_file, create_file, …) and secrets (use_secret), each checked against this function's operation map. Writes are checked against the declared fields.
call.progress(text)
A line the person sees while the function runs; nothing is kept.
call.ask(q, choices)
A card in the agent's name: at most 1,000 characters and 8 choices of 100. Unanswered after a day it returns None; the function's clock stops while it waits. With expects="file" the answer is a file ref.
call.post(text)
Speaks to the person now: at most 4,000 characters, three posts a call.
call.llm(…)
The chat's model, reached through the platform; the stored key never enters the worker. Requires llm: true.
call.credential(host, fields)
A login for a site the agent could not know beforehand, 1 to 20 fields, consented per agent and per site; the model sees labels only. Requires credentials: true.
call.propose(code, purpose)
Code up to 20,000 characters on a card, with the model's reading of it beside it. With code: true, an allowed card opens the hosts it named for that call, and call.install installs exactly the packages it named.
call.screen
A picture the person can watch and take over (§8.11).

Without a chat, as in a test, ask and propose return None and post returns False, so the same code runs everywhere.

Chapter 8

Execution nodes and the sandbox

The manifest decides what an agent is given. The sandbox bounds what its process can take, whatever its code tries. Agent code runs on an execution node, in a container that holds nothing else and has no route out but one proxy, as a user of its own, behind a file fence and a system-call filter.

8.1 The execution node

An execution node is one AI Runtime and its Execution Sandboxes, deployed together. The bundled node of a single-machine install is three Compose services. ai-runtime runs each chat's assistant, the executor and its gates, the agents' proxy (port 8002) and the sandbox registry (port 8005). sandbox is the same image started in another role: it runs the spawner (port 8003) and every worker. node-issuer holds the node-authority private key with no network at all and writes the node a fresh credential into a volume the runtime mounts read-only. A node on its own machine is the same three services, dialling a Data Core elsewhere, with no port open.

8.2 How a node links to the Data Core

Nobody registers a node. Trust is given once to an authority: a public key or a JWKS issuer, scoped shared or to one organization. Any node presenting a credential it signed is admitted, so a thousand nodes need no step each. The credential names the node, audience decentai-data-core, and optionally an organization and labels. It lives at most an hour; the bundled issuer signs ten minutes. The node never holds the authority's key, so a node taken over can sign for nobody and keeps its name for minutes.

The node keeps one WebSocket to /nodes/link, reconnecting after 1, 2, 4, 8, 15, then 30 seconds. The Data Core holds no node's address, so a node can sit behind a firewall that admits nothing. Everything the Data Core sends is signed: a reply names the node, its request id and the digest of the reply's bytes; a link frame names the node, the connection's nonce and its sequence. A node treats anything else as silence, because a reply can be a contract. A heartbeat every 20 seconds renews the node's chat leases, which last 60; every call for a chat carries its lease number, so two nodes can never act for one chat.

Code arrives through the package door, the only verbs a node principal may use: Agents:Package:List, the digests standing approvals pin; Agents:Package:Fetch, bytes by digest; and Agents:Package:Prepared, ready or failed. The runtime lists every ten seconds, which turns Preparing into Ready with no chat involved.

I-8.1

Nodes dial out and are admitted by authority, never by address. A node acts on nothing the Data Core's key did not sign for that node, and on no chat whose live lease it does not hold.

8.3 Environments built from approved digests

The runtime caches packages by content, one folder per digest. It checks bytes against the digest before writing, and the unpacked manifest against the approved hash before sending anything on. Tampered bytes therefore fail for everyone instead of poisoning a copy that many organizations share, and the runtime runs nothing from the cache.

Each sandbox keeps its own copy, and no folder is shared. Asked for a digest it lacks, it asks its runtime for the bytes. It checks digest and hash before writing, unpacks, and builds an environment keyed by the dependency list and interpreter, so a code-only update builds nothing. Then it starts one worker as installation's user, the verification start, to prove the package loads. A failure removes what its step made. Dependencies take two users, because a build is code too. The builder downloads and builds wheels through a pass that opens only pypi.org and files.pythonhosted.org. The spawner unpacks them and runs nothing of theirs.

I-8.2

Code reaches a sandbox only through its runtime, and is checked against the approved digest and manifest hash, both on the runtime and in the sandbox, before anything is written.

8.4 The worker pool

The worker pool keeps one worker per approval, not per digest, so nothing an agent holds in memory crosses organizations. A worker starts on first call, is kept warm for every chat of its organization, and keeps per-chat state such as a browser under call.conversation. It is disposable: replaced when its code changes, it crashes or it is ended for memory. The runtime places a new worker among eligible sandboxes: healthy, locks proven in the current process, not draining, holding the labels asked for. It prefers the one already running the agent, then one holding its package, then the least loaded (memory in 256 MB buckets, then processors in tenths), then takes turns.

8.5 The worker protocol

The worker is the SDK's worker loop, run by the agent environment's interpreter in isolated mode. Its argv is empty and its environment an allow-list that never holds the model key, the Data Core's trust key or the runtime's settings. Host and worker exchange newline-delimited JSON, protocol 2, at most 2 MiB a line; a malformed line ends the worker. Every worker request names its call_id and is answered from that call's operation map, only if the call was sent to this worker. Bytes whose base64 exceeds 256 KiB travel ahead as bytes pieces.

8.6 The runtime–sandbox link

Only its runtime commands a spawner. The two share one node secret, AI_RUNTIME_SANDBOX_SECRET, which Compose gives to nothing else, the Data Core included. The secret never travels. The side spoken to first sends a challenge, and the other answers with an HMAC-SHA256 under the secret with its role written in front, so one side's proof never passes as the other's. Every connection is TLS 1.3 with a key and certificate each process makes at start, so no certificates are issued or signed. Each proof covers the fingerprint of the certificate seen on that connection, so anyone in between fails both ways. A sandbox proves itself first on every request, and removes the secret from its environment so no worker inherits it.

8.7 Confining a worker

A small C program, the spawn helper, does the one thing the platform's user cannot: start a child as another user. It is compiled because a binary can carry that right and a script cannot. It refuses callers other than the platform's user and uids outside 20000–29999. In order, it sets limits, sets no-new-privileges for everything it will start, becomes the agent's user, applies Landlock to the paths the spawner named, and applies seccomp last. Each approval has its own uid per sandbox; the first uid is installation's, the last the builder's. A home is emptied, as its user, before every start.

Landlock lets a worker read the system, the browsers, its package and environment, and write its home. From ABI 4 it may connect over TCP only to the proxy port; from ABI 6 it reaches no abstract socket it did not create. Seccomp is a deny-list, because an allow-list would be a list of what somebody forgot. It refuses namespaces and mounts, ptrace, bpf, io_uring, module and keyring calls, and unneeded socket families. Each sandbox proves this at start and registers with what it proved. The runtime places no worker where confinement failed, and an agent's page states what a weaker kernel cannot enforce.

8.8 Network confinement

Three things leave the proxy as a worker's only way out. The sandbox's network is internal and joins only the runtime. At container start, the image's first step runs as root, the one step holding NET_ADMIN, and writes an nftables chain: for socket owners in uids 20000–29999, TCP to 127.0.0.1 on the proxy port is accepted and everything else rejected, DNS and the spawner included. It then becomes the platform's ordinary user and removes the capability from its bounding set, so nothing started afterwards can regain it. The spawner relays that port to the runtime's proxy, unread.

The proxy knows a worker by its pass and refuses a host the manifest does not name. It resolves the name itself, refuses the host if any answer is internal, and connects to the address it checked; it never opens TLS. Two kinds of host are lent per call: a from_secret host when use_secret hands over the credential, and a code card's hosts on the person's yes. Both close when the call ends. Every connection is written down with its owner, destination, bytes and duration.

I-8.3

A confined worker's only route off its machine is the runtime's proxy, and the proxy admits only hosts the approved manifest, a credential handed to the running call, or a card the person allowed names, at public addresses.

I-8.4

The host owns every clock. A worker cannot extend its own time, and a worker that does not answer a cancel is killed with everything its user runs.

8.10 Draining, many sandboxes, many nodes

One runtime serves many sandboxes. A second on the same machine is one more Compose service; one elsewhere needs only the node secret and the runtime's address. Nodes:Node:Drain drains one sandbox or all: no new worker starts there, running workers finish and retire, and the agent's next call is placed elsewhere. Sandbox labels such as gpu filter placement, though no manifest can ask for one yet. Labels on a node's credential are shown and gate nothing, because what a node says of itself is reported, not believed.

The Data Core places a chat on the node holding its lease, else among connected nodes that may serve the organization: its own first, then the chat's last node, then the least loaded. With placement: own_only nothing of the organization reaches a shared node. A chat that moves is rebuilt from the record; a call running on the old node is reported unknown, never rerun.

8.11 The live screen

An agent that drives something visible shows it with call.screen, undeclared, since a picture shows nothing a file could not. A frame, a JPEG or PNG of at most 300 KB, goes as screen.frame to the host, as screen_frame up the node link, and to the page. It is relayed, never recorded, and dropped rather than queued. The Browser agent sends 1,280-pixel frames: one per step, one every 0.35 s while the person holds it, one every 100 ms while they drive. Input returns the same road. The page sends AI:Chat:Screen, the Data Core checks that the person may write in the chat, and the node hands the events to the call that showed the screen, dropping them once it ends. Take over pauses the run; Hand back resumes it with the agent told to look again. Opening the screen calls the chat's watch: true function without the model, hence level 0 and no llm. Nothing of the browser is reachable from the person's machine.

What the sandbox does not do

It does not separate the people of one organization: a worker serves every chat of its approval, and a host lent to one call is reachable from another running beside it. It does not stop an agent misusing what it was rightly given. Memory is shared among agents and enforced by ending the largest. Before kernel 6.12, two agents that both intend to can share an abstract socket. The container, sharing the host's kernel, remains the outer wall.
