6 · Agents: a contract before code

Like a phone's permission screen, but stricter

An agent is a tool the assistant can use — Gmail, Google Sheets, a browser, a program runner, or something built for your own systems. Before any of its code runs, it must say, in a manifest, exactly what it will do, keep and reach. An administrator reads that, approves it, and from then on the platform holds the agent to it on every call.

Agents come from a public catalog or from your own repositories. Writing one for a system only your company has is the point: the same contract, the same checks, the same room. Two companies approving the same agent get separate copies, separate storage and separate processes.

Held to it on every call

The contract is not a promise the agent makes once. Every call is checked against the approved manifest (chapter 5); every file or password the agent asks for during the call is checked against what that function declared; every answer is checked against the outputs it described. The manifest the platform enforces is the stored, approved one — never one the running code supplies about itself.

7 · The sandbox

Every agent in a room of its own

Think of agents as guests in a hotel the platform runs. Each has a room their key opens and nothing else. Calls to the outside world go through one front desk, which connects them only to the people on their list. Some things nobody may do in the building at all. And the guests stay in a wing of their own, away from the office and the safe.

Five promises about an agent's code

  1. It reads and writes only its own files. Its home is emptied every time its process starts; other agents' rooms, the platform's code and its settings are out of reach.
  2. It runs as its own user, and cannot signal or stop anyone else's programs.
  3. It reaches only the hosts it declared, through the platform's proxy.
  4. It uses no more than it is allowed: limits on processes, open files and file size, a time limit per call, and a watcher that ends the largest agent before the machine runs out of memory.
  5. It may not ask the computer's core for what escapes are made of: new namespaces, tracing other processes, mounting file systems and the like are refused outright.

A small, carefully written starter program applies the layers in order — set limits, give up the right to gain privileges, become the agent's user, drop every special capability, put up the file fence, apply the system-call filter — and only then starts the agent. It is not a "run as administrator" program: a worker that runs it gains nothing.

One way out

An inspector, every time it starts

A sandbox you cannot see is one you have to take on faith. Each time the platform starts, it tests its own locks — starts a process as an agent's user, asks the kernel which fences it can enforce, prepares a room end to end, and tries the network the way an agent would — and writes down, in plain words, what holds. If agents cannot be given users of their own, the platform does not start. If a lock is weaker on a given machine — an older kernel without the file fence, a container started without the right to set the firewall — the platform says so plainly, and the operator sees exactly what is and is not enforced where it runs.

8 · Secrets

A vault, and a counter that lends one call at a time

Passwords, API keys and connected accounts live in a vault only the Data Core can open. When an agent's function needs one, it is lent for that call — to that agent's code and to nothing else.

Connected accounts

For Google, Microsoft and the like, you sign in once with the provider. The long-lived refresh token never leaves the Data Core; the agent is lent a short-lived access token, about an hour long, for the call.

Keys you type

An API key or a password you enter is lent to the agent's code as typed — an agent cannot use a key without having it. Reading the agent before approving it is the control for what it does with it.

Seeing is a filter

You see a credential only if you own it or it was shared with you; the check is part of the database query. Seeing is not changing: only its owner edits or deletes it.

Each agent keeps to its shelf

Records and files an agent keeps live in its own space. Another agent — even for the same person — cannot read them.

Honest edge

An agent's process is kept running between calls, so code that wanted to could keep a value it was lent. For an access token that is bounded by its expiry; for a typed key it is not. That is why agents are read before they are approved, and why the platform lends tokens rather than refresh rights wherever the provider allows.
